写在前面：这篇文章不是讲 Verilator 怎么用，而是讲怎么让验证平台自己判定对错。我用项目里真实的 zcle_aenc_wrapper 作例子——它有 CSR、literals 从接口、AXI 主接口、三路编码通道、错误注入和 debug 总线，是典型的”跑起来不崩、但很难确认结果对不对”的模块。

口径说明：文中的接口信号取自真实设计 zcle_aenc_wrapper.v；代码是按这些端口写的可运行骨架，你可以直接拷到项目里改路径使用。涉及项目内部的状态编码只做必要抽象，不影响平台结构。

1. 为什么”跑完不崩”不算验证通过

用 Verilator 仿真一个 RTL 模块，最低限度只需要：例化顶层、打时钟、复位、跑若干周期、打印一句 PASS。项目里已有的 verilator_sim_main.cpp 就是这么做的：

这能验证”编译能过、仿真不崩”，但回答不了三个真正重要的问题：

  1. 输出码流对不对？ 没有 golden，只有波形，肉眼不可能逐 bit 核对 256 bit × N 拍的 AXI 写数据；
  2. 回压/边界场景会不会出错？ 上游 ready 一直拉高、下游 AXI 一直 ready，等于没测握手与状态保持；
  3. 错误注入与 debug 总线是否按预期工作？ 这些功能不触发就永远是”未验证”。

一套可自检的平台，要把这三点变成机器可判定的结论：输入与 golden 同源、输出自动抓包重组、结果自动比对、异常自动报错退出。

2. DUT 接口分析：从 wrapper 端口推导平台组件

zcle_aenc_wrapper 的端口按功能可以分成五组，每组对应平台里的一个组件：

端口组 真实信号（节选） 平台对应组件
CSR 配置 csr_aenc_enable、csr_aenc_cmp_thr[31:0]、csr_aenc_error_int[1:0] driver 的配置阶段
literals 输入 zcle_lit_hist_qvalid/qdata[127:0]/qstrb/block_last/chunk_last/frame_last/qready stimulus driver
literals 读返回 aenc_lit_pvalid/rdata[127:0]/rresp/pready、aenc_lit_qvalid/qdata/qstrb 简化 AXI 从模型
码流输出 zcle_zpke_arith_m_axi_aw*/w*/b*（256 bit 写数据通道） AXI monitor + 码流重组
状态与调试 aenc_descrp_vld/rsp_data[63:0]、aenc_debug_info_bus[164:0]、aenc_error_int[1:0] scoreboard / 断言

平台设计的第一条原则由此确定：先按端口分组，再决定组件边界。不要写一个大而全的 main() 把所有信号堆在一起——那样回压逻辑、抓包逻辑、比对逻辑会互相纠缠，调试时无法定位是 driver 错了还是 DUT 错了。

5. C++ Testbench：驱动、抓包、自检

下面是平台主体。代码按 zcle_aenc_wrapper.v 的真实端口写，Verilator 生成的头为 Vzcle_aenc_wrapper.h。

5.1 工具函数与状态

关键点：monitor() 放在 step() 里、每个上升沿后调用，而不是写在 driver 循环里。这样无论 driver 做什么（发激励、等响应、故意停顿），monitor 都不会漏拍——抓包逻辑与驱动逻辑解耦是自检平台最重要的结构约束。

5.2 AXI monitor：把 256-bit 写数据重组为字节流

注意这里用的是 zcle_aenc_wrapper.v 里的真实端口：wdata[255:0]、wstrb[31:0]、wlast，地址高 6 位是 CBID。按 wstrb 抽取有效字节是关键——AXI 的最后一拍通常不是满 32 字节，直接把 wdata 全部写入会导致 golden 比对错位。

5.3 Driver：喂 literals 并随机化回压

回压随机化不是可选项。如果 awready/wready 恒为 1，AXI 写通道永远不反压，DUT 内部 store 状态机与 FIFO 的”暂停/恢复”分支就完全没被激励到。这里用 (rng()%4)!=0 和 (rng()%3)!=0 制造不同概率的反压，能在回归中触发大量平时遇不到的状态组合。

5.4 Scoreboard：自检判定

四条检查分别对应四类风险：数据错误、协议响应缺失、异常误报、死锁。只有四条全过，平台才打印 PASS 并返回 0——这就是”设计可自检”的含义：退出码本身就是验证结论，可以直接接 CI。

7. 让自检更可靠的四个实践

7.1 错误注入要专门跑一遍

zcle_aenc_wrapper 有 zcle_aenc_par_chk_en、zcle_aenc_err_ins[2:0] 和 csr_aenc_error_int[1:0]。自检平台应该有一个反向用例：打开错误注入，确认 aenc_error_int 确实拉起、并且 aenc_descrp_rsp_data 携带了错误码。否则”错误注入功能”在验证里等于不存在。

7.2 debug 总线做状态断言

aenc_debug_info_bus[164:0] 是内部状态观测口。与其只拿它打印波形，不如在 monitor 里加断言：

断言要围绕状态一致性，而不是”某信号等于某值”——后者一旦 RTL 重构就全部失效。

7.3 golden 与 RTL 用不同实现路径

项目 plan 里给出三种对齐方法，自检平台应按层次选用：

层次 方法 本平台对应
单元级 Verilator + DPI 调 cmodel，逐 bit 比对 unit/ 子平台
模块级 Python golden model，比对中间结果（ctx / lane_size / stream） make_golden.py 的元数据扩展
系统级 Verilator + cmodel DPI，AXI 输出逐 bit 对比 本文的 wrapper 平台

关键是 golden 不能由 RTL 反向生成。用 Python 独立实现、或从 cmodel 导出，才能形成真正的交叉验证。

8. 小结

给一套复杂 RTL 搭 Verilator 平台，真正要解决的问题不是”怎么让波形跑起来”，而是怎么让平台自己给出可信结论。本文用 zcle_aenc_wrapper 把这件事拆成四条：

  1. 接口分组决定组件边界：CSR / 输入 / AXI 输出 / 状态，各对应一个 driver 或 monitor；
  2. golden 与 stimulus 同源但异构：Python 独立生成，契约文件固定长度与种子；
  3. monitor 独立于 driver：抓包放在 step() 里，保证不漏拍；按 wstrb 抽取有效字节，避免最后一拍错位；
  4. 判定标准化：退出码 = 验证结论，比对、响应、异常、超时四类检查全过才 PASS。

这样搭出来的平台，不依赖人工看波形，可以直接接 CI；换一个 DUT，只需要替换端口驱动部分，monitor 和 scoreboard 基本可以原样复用。
