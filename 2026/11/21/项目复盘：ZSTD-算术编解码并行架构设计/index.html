写在前面：这是一个与视频编码无关的全新项目——面向通用数据压缩的 ZSTD 后端。它有自己独立的格式规范、状态机形态和接口假设，架构设计必须从 ZSTD 本身出发，而不是套用其他熵编码器的经验。文中”算术编解码”按项目里的功能称呼使用；需要先澄清的是，ZSTD 格式实际采用的是 FSE（tANS）与 Huffman，不是二进制区间算术编码，这是理解后面所有架构决策的前提。

口径说明：本文依据项目期间的个人工作记录整理，不涉及具体产品、工艺与内部代码。文中凡是”我的理解 / 取舍分析”，都与项目事实和格式规范分开标注。算法层面的细节对照公开规范与参考实现 docs/ZSTD/cmodel/zstd（FSE 状态机见 lib/common/fse.h）。

这是一个全新的通用压缩项目，与视频编码平台没有继承关系。ZSTD 有自己的格式规范、FSE/tANS 状态机与 Huffman 编码，接口假设和节奏约束都由这套格式决定。本文从 ZSTD 本身出发，把算法链路和硬件架构完整拆一遍。

2. 完整算法链路：从输入到码流

先不讲硬件，把算法走通。ZSTD 的压缩可以拆成五个阶段，后端（本文的主角）是第五阶段。

2.1 阶段一：分块与窗口

输入被切成若干 block（最大 128 KB）， frame 由多个 block 组成。block 头部 3 bit：last_block 标志 + block 类型（Raw / RLE / Compressed / Reserved）+ 块大小。Raw 块直接存原字节，RLE 块存单字节重复，只有 Compressed 块进入熵编码。

对硬件来说，这一步的意义是：块边界就是后端的事务边界，状态机不能无条件跨块携带。

2.2 阶段二：序列生成

Compressed 块内部把数据表示为两类对象：

  • 字面量（literals）：未被匹配覆盖的原始字节；
  • 序列（sequences）：每个序列是一个三元组 (offset, litLength, matchLength)，表示”跳过 litLength 个字面量后，从 offset 远处复制 matchLength 个字节”。

序列由 matcher 生成，参考实现按 strategy 分派：zstd_fast.c（哈希表）、zstd_double_fast.c（双哈希表）、zstd_lazy.c（greedy / lazy）、zstd_opt.c（最优解析），zstd_ldm.c 负责长距离匹配。这些属于压缩前端，不在本文后端范围内，但决定了后端看到的数据分布。

2.3 阶段三：长度与偏移转 code

序列的三个字段不直接编码数值，而是先转成 code + extra bits：ZSTD_seqToCodes()（zstd_compress.c:2709）把 litLength / matchLength / offset 映射为 LL code / ML code / OF code，高位部分作为附加位（extra bits）直接写入位流。这样做是为了让分布更集中，提高熵编码效率。

2.4 阶段四：字面量 Huffman

字面量用 Huffman 编码（zstd_compress_literals.c:169-178），可选单流（1X）或四流（4X），四流更适合并行解码。Huffman 表逐块自适应：新建表时把描述表写进 literals section header；若与上一块相同则用 set_repeat 模式，只写一个标志位。

2.5 阶段五：序列 FSE（tANS）—— 核心算法

三个 code 流（LL / OF / ML）各用一张 FSE 表编码（zstd_compress_sequences.c:291 起）。FSE 是 tANS（table-based Asymmetric Numeral Systems）的一种工程实现，状态数取 2 的幂，全部更新都化为查表与移位。

设当前状态为 state，表中预计算了 deltaNbBits 与 deltaFindState（fse.h:443-451 的 FSE_symbolCompressionTransform）。编码状态更新为：

$$nbBitsOut = (state + \delta_{nb}) \gg 16 \tag{1}$$
$$\text{BIT\_addBits}(state,\ nbBitsOut),\qquad state' = T\big[(state \gg nbBitsOut) + \delta_{find}\big] \tag{2}$$

式 (1)(2) 的含义：先把 state 的一部分高位比特输出到码流，再用剩余高位查状态表 T 得到下一状态与对应符号。它的概念形式是 ANSI 状态更新 (state’ = (state \ll nbBits) + bit - lowBound)，但 -lowBound 已被预计算进表里，硬件只需一次加法、一次移位、一次查表。

解码状态更新是逆过程（fse.h:532-537）：

$$state' = newState + \mathrm{BIT\_readBits}(nbBits),\qquad newState = (nextState \ll nbBits) - tableSize \tag{3}$$
$$symbol = \mathrm{SymbolTable}[state'] \tag{4}$$

式 (3)(4) 中 nbBits 与 newState 来自解码表项，tableSize 是状态数。解码器读 nbBits 位拼到 newState 上得到新状态，再查符号表输出符号。编码端按 LL→ML→OF 逆序 flush 三个状态（zstd_compress_sequences.c:371-376），解码端按相反顺序恢复。

FSE 表同样是逐块自适应：参考实现用 ZSTD_selectEncodingType() 为每张表选择 set_basic（不写表）、set_rle（单符号）或 set_compressed（写 normalized count，zstd_compress.c:2800-2893），并支持 set_repeat 复用前块表。

2.6 解码链路

解码是上述过程的逆序：读 block header 判类型 → 恢复 Huffman 表与 FSE 表（或 repeat）→ Huffman 解码字面量 → FSE 解码 LL/OF/ML code 与附加位 → 按序列重建输出（复制字面量 + 从 offset 复制匹配段）。硬件上更难的是：状态恢复、符号判决、表访问是强串行的，且必须处理”码流何时结束”。

3. 后端接口：从格式结构倒推

ZSTD 的 frame → block → literals/sequences 结构不是实现细节，而是接口设计的输入。算术编解码后端处在这条链路的末端。

从格式倒推接口，有三个约束必须在架构阶段确定：

  1. 块边界即事务边界：FSE/Huffman 状态不能无条件跨块携带，块结束时必须给出确定的状态 flush 与码流边界；
  2. 流式输入：上游不会等整帧缓存完，数据以流的方式到达，接口必须支持背压；
  3. 码流组织与局部存储协同：输出不是裸字节流，要按 block / frame 组织并写表头，这部分要和缓冲一起设计。

我的理解：如果等 RTL 写到一半才处理块边界和码流组织，几乎一定要返工。

4. 硬件架构分析

4.1 顶层：控制、计算、输出三层分治

这是整个后端最核心的架构决定。FSE 后端的状态更新逻辑复杂、表访问多、模式切换多，如果把所有逻辑堆在一个大模块里硬顶，时序和验证都会失控。我按三层拆分：

层 职责 为什么不合并
控制层 块类型判决、表模式（basic/rle/compressed/repeat）、边界状态机 状态多、与数据无关，合并会把长控制路径压进数据关键路径
计算层 FSE 状态更新、Huffman 编解码、附加位拼装 串行依赖强，需要独立流水与短关键路径
输出层 码流 FIFO、表头写入、block/frame 组装、DMA 回写 节奏与下游消费相关，用 FIFO 解耦才能稳定吞吐

这套分法是从 ZSTD 自身的复杂度分布推导出来的：表模式、块类型、边界控制属于与数据无关的长状态路径；FSE 状态更新属于强串行的短环；码流输出节奏随下游变化。三者必须拆开，才能同时满足时序与吞吐。

4.2 编码数据通路：状态环与流水切分

FSE 编码的关键路径在状态更新环：当前状态要先输出高位、再查表得到下一状态，下一个符号才能继续。我的流水切分是：

流水级 操作 关键路径特征
S0 符号/表项预取 与状态无关，可提前
S1 nbBitsOut 计算 + 位输出 一次加法 + 移位
S2 状态查表跳转 表访问，组合路径较长
S3 位流拼接与缓冲 与 S1/S2 弱耦合，FIFO 解耦

三个 code 流（LL/ML/OF）各有独立状态，可以并行推进，最后按格式要求的逆序 flush。三条状态环彼此独立，天然提供了并行度：硬件上可以做三份状态寄存器、共享一套状态更新组合逻辑，用时间复用换取面积效率。

4.3 解码数据通路：更短的环、更严的序

解码端的状态恢复是式 (3) 的加法与式 (4) 的表查，组合路径比编码端短，但顺序约束更严：必须先读够位、恢复状态，才能查符号表，进而决定下一符号的码长。因此我把”位缓冲预取”和”状态恢复 + 符号判决”分成两级，让位读取提前进行，缩短主环。

4.4 流式接口与回压控制

ZSTD 的输入是流式的，块长可变，数据到达速率随内容分布变化。接口不能假设”每拍都有数据”，也不能假设”下游每拍都能收”，这决定了入口 FIFO 与出口节流必须作为主架构的一部分设计。

  • 入口 FIFO 吸收上游突发，避免直接背压到上游；
  • 出口按码流消费能力控制输出，避免堆积；
  • 中间级用 valid/ready 握手，让回压逐级同步传播。

我的理解：回压控制不是加 FIFO 就解决了。真正要解决的是状态一致性——流水因回压暂停时，FSE 状态、位缓冲指针、FIFO 指针要停在同一拍，否则恢复时状态错位。

4.5 块边界处理

块边界是 FSE/Huffman 后端最容易出错的地方：

边界类型 风险 处理方式
状态跨块 上一块状态误带入下一块 块结束强制 flush，状态显式复位/保存
表复用 repeat 标志与实际表不匹配 表模式单独状态机管理，与块边界对齐
码流对齐 残差字节处理错导致后续全错 按格式要求做字节对齐与边界标记
部分块 数据不足一个完整块 单独路径处理，避免污染主流水

验证阶段我把块边界作为重点风险点单独建用例。边界错误不会在出错那一刻暴露，而是在后续以”码流完全错位”的形式出现，定位成本很高——这也正是状态机型编码器的典型验证难点。

4.6 片内缓存协同

ZSTD 的码流组织涉及大量小块搬运。我把片内缓存当主架构的一部分设计：

  1. 块级缓冲复用：字面量与序列的临时存储复用同一组 SRAM，通过时隙划分避免冲突；
  2. 码流输出配合：编码输出先进入片内缓冲，按 block / frame 组织后批量写出，避免零散小访问；
  3. 表存储：FSE/Huffman 表放片上，按块更新，repeat 模式避免重复搬运。

结论是：片上存储不是附属细节，而是吞吐能否成立的前提。ZSTD 的块大小不固定、表逐块自适应，缓冲组织必须比固定块大小的场景更灵活。

5. 工程收敛：详细设计、验证、Lint 与综合

环节 做法 为什么重要
C cmodel 比对 与官方参考实现做 bit-true 对齐 FSE 状态机对 1 bit 错误零容忍
定向用例 块边界、表模式切换、长序列压力 随机用例覆盖不到边界组合
回压验证 人为制造上下游速率差 验证状态在暂停/恢复时的一致性
Lint / 综合 早期介入，不等 RTL 写完 流式接口时序问题要早发现

熵编解码的验证特点是错误会传播：一个状态跳错，后面的码流全部错位。比对粒度越细越好——在状态级、符号级定位”第一个错误”，比只做码流级比对高效得多。

6. 复盘：五条原则

  1. 先看清算法形态再谈架构：ZSTD 是 tANS + Huffman，状态更新是”输出高位 + 查表跳转”，不是区间除法。架构必须从这套状态机形态推导出来；
  2. 格式结构决定后端接口：frame / block 结构与表模式是接口设计的输入，块边界必须在架构阶段处理；
  3. 按稳定吞吐设计，不按峰值吞吐设计：通用压缩输入分布变化大，最坏分布下仍要保持流水稳定推进；
  4. 回压控制的核心是状态一致性：暂停/恢复时，状态、位缓冲指针、FIFO 指针要停在同一拍；
  5. 边界错误要单独验证：块边界、表复用、码流对齐都要有定向用例，不能只靠随机码流。

7. 常被问到的问题

Q1：ZSTD 的熵编码后端到底做什么？

两件事：字面量用 Huffman 编码（1X / 4X 流），序列的 LL / ML / OF 三个 code 用 FSE（tANS）状态机编码。后端负责把字面量与序列变成符合 frame / block 格式的码流，以及反向恢复；核心是 tANS 状态更新、表逐块自适应和块边界收尾。

Q2：FSE 的状态更新为什么能只用查表和移位？

因为 tANS 把 (state - lowBound) 预计算进状态表（deltaNbBits / deltaFindState），硬件只需”输出高位 + 查表跳状态”，避开了通用算术编码里的乘法与除法。

Q3：为什么块边界要单独处理？

因为状态机有记忆，块结束必须 flush；表还可能 repeat 前块。边界处理错了不会立刻暴露，而是后续以码流完全错位的形式出现，定位成本很高。

Q4：ZSTD 有两条 Huffman 流和三条 FSE 流，硬件要各做一套吗？

不必。编码器侧多路状态可以共享同一套状态更新数据通路，按时间复用；解码器侧同理。关键是把”状态寄存器组”做成多份、”状态更新组合逻辑”做成一份，用面积换时序的代价最小。

Q5：这个项目对后续设计有什么沉淀？

两条：一是为通用压缩后端沉淀了可复用的”tANS 状态机 + 流式接口”骨架；二是把”表逐块自适应 + 流式输入 + 块边界收尾”这套约束下的架构方法固定下来，为后续类似的压缩后端设计提供直接参考。
