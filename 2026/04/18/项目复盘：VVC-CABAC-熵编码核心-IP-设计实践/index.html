2. 从规格倒推：CTU 周期预算

CABAC 处在 CTU 级流水里，它的规格本质上是一个问题：每个 CTU 给多少拍，够不够把这个 CTU 的所有 bin 编完？

2.1 两种协议按同一像素吞吐做预算

两种协议的 CTU 尺寸差 4 倍，周期预算也正好差 4 倍。这说明预算是按同一像素吞吐定的：上游流水按像素率推进，CABAC 不能因为协议不同而成为瓶颈。在 1.2 GHz 下，单路约 327 Mpixel/s。

2.2 用规范约束校核：1 bin/cycle 够不够

最坏情况下，常规 bin 主要来自系数编码。用规范给出的上界校核：

HEVC（64×64） VVC（128×128）
每 CTU 系数数（4:2:0） 6144 24576
系数常规 bin 上界 每 4×4 子块最多 16 个 sig、8 个 gt1、1 个 gt2，平均约 1.56 bin/系数 → 约 9600 remBinsPass1 限制为 1.75 bin/系数 → 43008
占 CTU 周期预算 约 64% 约 72%

在 1 bin/cycle 下，系数部分的常规 bin 最坏情况落在预算之内，并给划分、预测模式、MVD 等其他语法留出约三成余量。VVC 的常规 bin 预算机制（原理见深度解析 2.3 节）正是让这笔账能算清楚的前提。

2.3 接口搬运不能吃掉预算

环路滤波级送给 CABAC 的数据以 128 bit 位宽、valid/ready 握手传输，每个 CTU 以 start/end 标记首尾。按每拍的有效载荷计算：

数据 VVC（每 CTU） HEVC（每 CTU） 说明
系数 3072 cycle 768 cycle 16 bit/系数，一拍 8 个，按 Y→U→V、4×4 CG 内 raster 顺序
块信息 3584 cycle 896 cycle 每个 4×4 块一份，约 3.5 cycle/块
上方邻块信息 48 cycle 24 cycle CTU 上边界的 4×4 块
合计占预算 约 11% 约 11%

输入搬运只占预算的十分之一左右，并且和编码过程以 FIFO 解耦，不会成为瓶颈。两种协议的占比也几乎一致，说明接口位宽是和周期预算一起设计的。

3. 顶层架构：控制骨架 + 四级后端

图中 DDR 的三类交互：(1) offline/bypass 模式下语法信息的写出与读回；(2) 多核协同时加载上下文表；(3) CTU 码流写出与帧级拼接。

模块 职责
prepare 统一数据来源：online 时把 LF 数据直接透传给后级；bypass 时把数据写入 DDR；offline 时先写 DDR 再读回送往后级
pack 按协议的编码顺序打包语法元素，完成大部分二值化，把 bin 任务压入 FIFO
aenc 剩余语法的二值化 + 上下文读写 + 二进制算术编码；VVC 有两个编码实例
frame bs gen 把 CTU 级码流片段组织成 WPP 行级、帧级码流
regbank + top ctrl 读取配置，向各级下发协议选择、工作模式、ALF 编码路径、帧尾拼接等控制

把控制骨架单独抽出来，是这个设计里很关键的一点：模式、协议、ALF on/off、多核与帧尾拼接的组合非常多，如果分散在各子模块里隐式判断，验证会失控。

3.1 三种工作模式

模式 数据路径 用途
online LF → prepare 透传 → pack → aenc 正常 WPP 编码，片上直连，延迟最低
offline LF → prepare → DDR → 读回 → pack → aenc 上下游解耦，CTU 信息经 DDR 缓冲
bypass LF → prepare → DDR 硬件只落盘 CTU 信息，熵编码交由软件完成

bypass 模式的存在有一个具体原因：HEVC 硬件 CABAC 只支持 WPP 编码，状态机里没有非 WPP 的跳转逻辑。非 WPP 的 HEVC 码流由软件完成熵编码，硬件只负责把信息写出来。这是用“软件兜底”换取硬件状态机简化的一个取舍。

4. 双协议复用：共享什么、分开什么

这是复盘里最想讲清楚的一点，因为它和“直觉答案”不一样。

4.1 项目里的实际做法

层次 共享还是分开 具体做法
LF→CABAC 接口 共享 两种协议共用同一套接口数据类型；HEVC 模式下 pack 从中挑出 HEVC 需要的字段
输入 info buffer 共享 只保留一套缓冲，经“协议选择”路由到两个 pack；HEVC 的信息复用 VVC 的存储空间
pack 两套电路 HEVC pack 复用上一代编码器中成熟的模块；VVC pack 新开发
算术编码 两套硬件 两种协议的概率模型不同，分别实现
帧级码流组织、DMA、控制骨架 共享 与协议无关

共享 info buffer 的直接收益，是省掉了一份输入缓冲，以及 pack→aenc 之间的一部分 FIFO。HEVC 的信息格式是上一代设计定义的（每个 8×8 块占 256 bit），因此做了一层格式适配，让它落在 VVC 定义的存储空间里，而不是让旧模块去理解全部新字段。

4.2 为什么算术编码不共享（我的理解）

深度解析 6.5 节从理论上讲过“算术编码引擎与协议无关，可以共享”。项目最终选择了两套，我认为有三个原因：

  1. 概率模型就在 1 bin/cycle 的关键环路里。HEVC 是查表状态机，VVC 是双速率估计器加乘法求 LPS，两者的关键路径形态不同。合成一套电路，就要在 Range 环里多插一级选择，并让两种协议的最坏路径叠加；
  2. HEVC 侧可以直接复用成熟模块。已经流片验证过的 HEVC 编码通路，比为了共享而重写的新电路风险低得多；
  3. VVC 本来就要两个编码实例（见 4.3 节），“共享”的收益被进一步稀释。

代价是协议间的空闲硬件：VVC 模式下 HEVC 的算术编码器不工作，反之亦然。这部分可以靠门控降低动态功耗，但面积省不下来。这是一个用面积换时序收敛与交付风险的有意识取舍。

4.3 ALF on / off：VVC 为什么一个 CTU 编两遍

VVC 模式下，aenc 有两个编码实例，分别对应 ALF on 和 ALF off 两种情况，每个 CTU 同时产生两路码流并写入 DDR；是否启用这两条路径，由序列级的 ALF 使能开关决定。

原因在于数据依赖的时序：ALF 的滤波参数要在帧级统计之后才能确定，而 CABAC 作为 CTU 流水的一级，必须在帧级决策出来之前就把 CTU 编完。与其让 CABAC 等待（这会打断整条流水），不如两种可能都编一遍，等帧级决策确定后再选用。这是一个典型的用冗余计算换掉流水停顿的设计。

5. pack 与 aenc 的分工：bin 任务接口

5.1 二值化放在哪里

二值化不是只在一个地方做的，而是按语法元素的性质拆在两级：

在 pack 中二值化 在 aenc 中二值化
二值化后全部是常规 bin 的语法元素 全部走 bypass 的语法元素
二值化后部分常规、部分 bypass 的语法元素 需要先拆成 prefix + suffix 的特殊语法元素，如 last_sig_coeff_x/y 的前后缀、cu_qp_delta_abs：pack 只负责拆分，prefix 的 TR、suffix 的 EG0 在 aenc 中完成

pack 把二值化结果连同每个 bin 的 ctxInc 和类型（常规 / bypass）一起压入 FIFO，供 aenc 消费。

这样分工的一个直接好处（我的理解）：全 bypass 语法元素以“值”的形式穿过 FIFO，在 aenc 内部紧贴 bypass 引擎展开成 bin。FIFO 上传递的是一个值而不是一串 bin，bypass 4 bin/cycle 的吞吐才不会被级间接口的带宽卡住。

5.2 一个约 30 bit 的任务字

pack 送给 aenc 的不是裸 bin，而是一个约 30 bit 的任务描述字：

字段 含义
值（16 bit） 待编码的单 bin 或多 bit 值
联合字段 随编码方式复用：单 bin 时为 ctx 索引；TR 时为 cMax 与 cRiceParam；定长时为 cMax；EGk 时为阶数 k
编码方式 ONE（单 bin）/ TR（截断 Rice）/ FLEN（定长）/ VLEN（k 阶指数哥伦布）
语法类别 用于在 aenc 中确定该语法元素上下文表的基地址

这个接口的设计思路是：pack 只描述“编什么、怎么二值化”，aenc 自己展开并定位上下文。字段按编码方式复用，用一个窄接口覆盖了全部语法元素。

6. WPP、多核与码流拼接

场景 处理方式
单核 WPP CTU 码流按 WPP 行的顺序写入 DDR；一帧结束时（非多核、非 low-delay），CABAC 把每个 WPP 行的码流读回，拼接成整帧码流后写回 DDR
多核 帧级拼接由 core 外部专门的 DMA 模块完成；跨核协同编码时，aenc 从 DDR 加载上下文表
low-delay 不做帧尾的整帧拼接
HEVC WPP 上下文同步 在 CTU 行的第 2 个 CTU（ctu_x == 1）完成后保存上下文，供下一行起点继承，与规范一致

这里体现的是一个边界划分：“CTU 编得对”和“整帧码流组织得对”是两件事。前者在 aenc 里解决，后者交给独立的码流组织模块和 DMA。多核场景下上下文要跨核传递，走 DDR 是最直接的办法，代价是行起点要等待上下文加载。

7. 综合阶段遇到的三个真实问题

这一节是工作记录里最有价值的部分。三个问题有一个共同点：都不在大家最先想到的“算术编码关键环路”上。

7.1 面积：一个新功能让编码核面积翻倍

背景：项目中期，CABAC 新增了一个功能：在编码过程中估算不同帧类型下的码率，用于帧类型（slice type）决策。

现象：重新综合后，

范围 面积变化
CABAC 整体 +5.9%
VVC 算术编码部分 +65.6%
单个 VVC 编码实例 约 ×2
其中帧类型更新逻辑本身 增量的一小部分

根因：膨胀集中在编码实例的前级。为了做码率估算，实现中例化了 3 份上下文表（可以理解为对应 VVC 的 3 种上下文初始化类型），每份是 379 个上下文 × 38 bit 的寄存器，再加上一个较大的统计累加逻辑，并且修改了部分存储位宽。由于 VVC 有 ALF on/off 两个编码实例，这些开销又被乘了 2。

优化方案（记录中的分析结论）：合并码率统计所用的上下文表，并收窄一个标志信号的寄存器位宽，预计可收回本次新增面积的约七成。

复盘延伸（我的理解）：38 bit/ctx 正是参考软件 VTM 的数据表示；按 VVC 规范的有效位宽只需 28 bit/ctx（推导见深度解析 4.3 节）。对于“码率估算”这类只需要近似状态的辅助功能，还可以考虑更低精度的状态表示。这个案例让我意识到：新功能的面积评估要在写 RTL 之前做，而不是综合之后才发现。

7.2 时序：违例路径在 DDR 地址生成里

现象：时序违例的路径不在 Range 环，而在 prepare 的语法写出通路中：offline / bypass 模式下计算 DDR 写地址的乘法器。路径是一长串全加器进位链，即使综合工具已经做了 retiming，依然违例。

根因分析：DDR 地址形如 base + index × stride，乘法和进位链在 1.2 GHz 下放不进一拍。这类路径在架构评审时很容易被忽视，因为它“只是地址计算”，不在算法核心里。

常见的处理方式：

方案 思路
增量地址 地址按 CTU / 行顺序递增，用 addr += stride 替代乘法
预计算 index × stride 中的不变部分在帧起始时由配置计算好
多拍乘法 地址不是每拍都变化，允许多拍完成，并对时序工具声明多周期路径

教训：高频设计做时序预算时，要把“控制面”的算术也列进去。地址、计数器、阈值比较这类逻辑数量多、位宽宽，往往比算法核心更早撞上时序墙。

7.3 扇出：一个寄存器 FIFO 的写指针扇出 3.7 万

现象：综合报告提示，prepare 中一个与 WPP 相关的 FIFO，其 7 bit 写指针的每一位扇出约 36870，超出 20000 的上限；对应的门控时钟单元也同样超限。

根因：这个 FIFO 用寄存器堆实现，深 128 × 宽 288 bit（36864 = 128 × 288，与扇出数一致）。写指针要译码成每一个存储位的写使能，于是每一位指针都要驱动全部 36864 个存储单元。

常见的处理方式：

方案 适用条件
改用 SRAM 宏 容量达到这个量级时，SRAM 的面积与功耗通常都更优，扇出问题自然消失
分 bank + 指针复制 必须用寄存器时，按宽度或深度切分，每个 bank 配一份指针寄存器
重新评估深度 确认 128 深是否是最坏情况的真实需求，还是“保守取大”

教训：FIFO 的“深 × 宽”不只是存储容量问题，也是扇出与布线问题。超过几千 bit 的缓冲，在架构阶段就应该决定用寄存器还是 SRAM。

8. 验证与签核

环节 做法
参考模型 与 C cmodel 做 bit-true 比对，覆盖 HEVC/VVC 双协议、多种工作模式
签核 综合、功耗分析、覆盖率收敛（code 98% / functional 100%）

CABAC 的错误会向后传播：一个 bin 错了，后面的码流全部错位，往往要很久之后才在解码端暴露。所以比对粒度越细越好，在 bin 级、上下文级定位“第一个错误”，比只做码流级比对高效得多。模式越多（3 种工作模式 × 2 种协议 × ALF on/off × 单核/多核），控制骨架越需要单独的定向用例覆盖。

9. 演进：下一代中的上游信息通路改造

在下一代演进中，我主导了 CABAC 上游信息通路与接口的改造。核心问题是：offline 模式下，上游信息要经 DDR 往返，周期预算够不够？

方法上，我坚持用“格式上界”而不是“典型场景”做预算：按语法上可能出现的最大信息量构造每个 CTU 的输入，要求最坏情况下的处理周期仍小于 CTU 周期预算。

场景 处理周期 / 周期预算
格式最坏上界 约 90%（保留约 10% 余量）
稠密场景 约 78%
真实码流 不足 10%

真实码流和最坏情况相差一个数量级，只用真实码流评估会严重高估余量。早期“每拍输出 1 字节”的方案在最坏上界下会超出预算，改为每拍最多 2 字节后才满足判据；这个结论只有用格式上界测才能得出。配套地，我用 Python 实现了与 RTL bit-true 对齐的参考模型作为 golden 生成器，并让 golden 数据头带上协议标志，读侧与寄存器配置交叉校验，防止 HEVC/VVC 数据混用。

10. 复盘：四条原则

  1. 规格从预算反推：CTU 周期预算、1 bin/cycle、接口位宽是一起定的。用规范的常规 bin 上界校核，两种协议都留有约三成余量；
  2. 复用要分清“壳”和“核”：缓冲、调度、码流组织这些“壳”共享；处在关键环路上、协议差异大的“核”分开做。省面积不是唯一目标；
  3. 用冗余换掉停顿：ALF on/off 两路同时编码，用面积换来不等待帧级决策的流水；
  4. 收敛问题常常不在算法核心：面积膨胀出在辅助功能，时序违例出在地址乘法，扇出超限出在 FIFO 实现方式。架构评审时要把“非核心”逻辑同样列进 PPA 预算。

11. 常被问到的问题

Q1：CABAC 为什么能做到 1 bin/cycle？够用吗？
关键路径是 Range 环（原理见深度解析第 6 节）。是否够用要看 CTU 周期预算：VVC 系数常规 bin 的上界（1.75 bin/系数）约占 60000 cycle 预算的 72%，HEVC 约占 64%，在 1 bin/cycle 下都有余量。

Q2：双协议是怎么复用的？
共享接口、输入缓冲、控制骨架、码流组织与 DMA；pack 和算术编码按协议各做一套，HEVC 复用上一代成熟模块，VVC 新开发，通过协议选择信号选通。

Q3：为什么不把两种协议的算术编码合成一套？
概率模型位于 1 bin/cycle 的关键环路内，合并会让两种协议的最坏路径叠加；HEVC 侧复用已验证的模块风险更低；VVC 本身已需要两个编码实例。用面积换时序收敛与交付风险。

Q4：VVC 为什么每个 CTU 输出两路码流？
ALF 参数要在帧级统计后才能确定，而 CABAC 在 CTU 流水里不能等待。两种情况都编一遍，等帧级决策确定后选用其中一路。

Q5：bypass 为什么能做到 4 bin/cycle？
算法上，连续 bypass bin 不改变 Range，可以合并为一次移位加；接口上，全 bypass 语法以“值”的形式穿过 FIFO，在 aenc 内部展开，不受级间 FIFO 带宽限制。

Q6：多核时上下文怎么传递？
跨核协同编码时，编码核从 DDR 加载上下文表；帧级码流拼接由 core 外的 DMA 完成。
